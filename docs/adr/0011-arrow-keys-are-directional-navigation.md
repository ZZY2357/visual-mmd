# 画布方向键是「方位导航」，不是「结构导航」

画布方向键原先按**语法/树关系**定义落点（flowchart 走源码顺序、mindmap 走父/子/兄弟），但 mermaid 的
布局与源码顺序无关：flowchart 交给 dagre 分层，mindmap 交给 cose-bilkent 力导向。真机实测（2026-09-29）：
flowchart 从 B 按 `→` 跳到**正下方**的 C、从 C 按 `→` 跳到**右上**的 D；mindmap 从「双面板同步」按 `↓`
跳到**右上**的「属性面板」、从根按 `→` 到的是**左下**的第一个子节点。方向键的字面承诺是「往那个方位走」，
落点却由书写顺序与力导向随机性决定——这就是用户报的「上下左右键切换选中特别严重」。

因此改为**方位导航**：以当前选中节点的**可视范围中心**为锚点，在该按键所指方向的 45° 锥形范围内
（如 `→` 取 `dx > 0 && |dy| ≤ |dx|`）取**中心距离最近**的节点为新选中；距离并列时按投影顺序取先者；
无候选则无操作（不回绕）。四个图种（flowchart / mindmap / class / sequence）同一套语义。无选中时没有
锚点、方位无从谈起，回落为「选中投影第一个节点」——与改前的既有行为逐字一致。

**代价是 mindmap 失去树形四向语义**（`←` 不再保证回到父节点）。这是权衡后接受的主要代价：四个方向键
只有四个方向，而树关系有父/子/前兄弟/后兄弟四种，把后者映到前者本就是任意的；几何语义则自带屏幕上
可立即验证的预期——按 `←` 选中的节点绝不会出现在右边。

被否掉的替代方案：(a) 只修 flowchart、保留 mindmap 树语义（原工单 03 的范围）——力导向布局下树语义
同样不符字面承诺；(b) 结构优先 + 几何兜底（有父节点就跳父节点，否则按方位）——两套规则混用后「按 `←`
会去哪」不再可预测；(c) `←/→` 按结构、`↑/↓` 按方位——同一排按键两套心智模型。

配套约定（同批定案）：任何修饰键（Ctrl/Cmd/Alt/Shift）按住时都**不导航**，但仍 `preventDefault`
（否则 `Alt+←`、`Cmd+←` 会触发浏览器前进后退；也修掉 `Shift+方向键` 静默改选中的缺陷）。节点位置取自
**渲染后的 DOM 实测**（`getBoundingClientRect`），所以这是导航第一次依赖渲染产物——happy-dom 渲染不出
mermaid，故把「按位置挑候选」抽成纯函数、DOM 测量留在适配层（见工单 14）。
