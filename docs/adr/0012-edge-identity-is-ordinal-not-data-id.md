# 连线的身份是「位置序」，不是 mermaid 的 data-id

> **状态：accepted**

画布要让 `class` 的关系边与 `sequence` 的消息线可点选、可右键，就必须给每条连线一个**身份**，
否则「右键了哪条线」无从回答。自然的选择是沿用 ADR-0007 对节点的做法——把 mermaid 渲染出的
`data-id` 当身份（de facto hook）。

**2026-09-29 真机实测否掉了这条路**：`data-id` 会随编辑重排。

- **class** 关系边 id 形态 `id_{源}_{目标}_{N}`，`N` 是全局自增计数器。**末尾追加**一条关系时原有 id
  逐字不变；但**中间插入**一条时，插入点之后的 id 全部重排（`id_Customer_Account_2` →
  `id_Customer_Account_3`、`id_Account_Ledger_3` → `id_Account_Ledger_4`）。
- **sequence** 消息线的 id 是纯序号 `iN`。中间插入一条消息后，插入点之后的元素全部重排
  （自消息 `i6`→`i7`、Note `i4`→`i5`、loop 块 `i7`→`i8`）。

致命之处在于**"末尾追加安全"对本 app 毫无价值**：右键菜单的加关系/加消息按 `afterElementId`
落在右键节点之后（即中位插入），正好是最坏场景。

**因此连线身份改用位置序**（投影顺序，如 `class-relation:2`、`message:3`）。它在 app 里天然稳定——
parser 已知每条连线在源码的哪一行；且它是**我们自己算的**，可测可控，不依赖 mermaid 的私有实现细节。

**明确否掉的方案**：(a) 「`data-id` 优先 + 位置序回退」的混合口径——两个来源混用会让"这条线的身份
是什么"变成运行时条件决定，调试时无法预期；既然位置序够用，就不引入第二个来源。
(b) 每次渲染后重建 `data-id` → 语义的映射并缓存——缓存必然在插入后失效，等价于每次都重建，
还不如直接用位置序。

**代价**：连线的位置序会随插入重排，即"选中态在编辑后可能指向另一个元素"。这个代价被接受，因为
本 app 每次编辑都重渲染、本来就不保证选中跨编辑存活（节点也有同样性质）。

**注意与节点口径的差异**：节点的 `data-id`（类名、参与者名）是**稳定**的，所以 ADR-0007 对节点仍然
成立；本 ADR 只针对**连线**。实测同时确认了这一点：插入消息后，参与者 `使用者`/`系统`/`存储` 的
`data-id` 逐字不变。
